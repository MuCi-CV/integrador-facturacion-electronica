# Migración a Python 3.10 + Django 5.2 LTS — Plan de implementación

> **Para trabajadores agénticos / For agentic workers:** REQUIRED SUB-SKILL (sub-skill requerido): usar
> superpowers:subagent-driven-development (recomendado) o
> superpowers:executing-plans para implementar este plan tarea por tarea.
> Los pasos usan checkboxes (`- [ ]`) para seguimiento.

**Goal:** Llevar producción de Python 3.7.17 + Django 3.2.25 a Python 3.10 + Django 5.2 LTS,
con el venv anterior intacto como rollback de una línea.

**Architecture:** Venv paralelo en una ruta nueva, validado con producción corriendo normal;
después se cambia `ExecStart` del unit de systemd. Entre 3.2.25 y 5.2.17 **no hay migraciones
internas nuevas**, así que el `migrate` es no-op y el rollback es completo: no queda estado de
base adelantado.

**Tech Stack:** Python 3.10 (`/usr/bin/python3.10`, ya instalado en Ubuntu 22.04.5), Django
5.2.x, DRF ≥3.16, drf-yasg 1.21.15, PyMySQL vía `install_as_MySQLdb()`, gunicorn, MariaDB,
systemd (`mucintegrador.service`).

**Spec:** `docs/superpowers/specs/2026-08-28-django-52-lts-design.md`

## Global Constraints

- **Rama:** todo el código va en `feature/django-52-lts`. Nunca commitear a `main` directo.
- **Python de producción:** `/usr/bin/python3.10`. NO usar `python3` pelado: en ese servidor
  apunta a 3.10 hoy, pero el 3.7 sigue instalado y el histórico del proyecto tiene un
  incidente por asumir a qué apunta.
- **Venv viejo INTOCABLE:** `/root/.local/share/virtualenvs/integrador-ObaHlHmv` es el
  rollback. No borrarlo, no actualizarlo, no reinstalar nada dentro.
- **Venv nuevo:** `/root/venv-integrador-52`, creado con `python3.10 -m venv`, **sin pipenv**
  (pipenv derivaría la ruta del hash del proyecto y reusaría el venv viejo).
- **Django 5.2, no 6.** El shim de PyMySQL reporta `version_info = (1, 4, 6)`; Django 5.2
  exige `≥ (1, 4, 3)` y arranca, Django 6 exige `≥ (2, 2, 1)` y lanza `ImproperlyConfigured`
  al arrancar.
- **Settings de producción:** `muci-integrador.settings`. Settings de tests:
  `muci-integrador.test_settings`.
- **Todo script de diagnóstico contra el settings real** debe desconectar Sentry
  inmediatamente después de `django.setup()`, o queda registrado como cliente de producción:
  `sentry_sdk.get_global_scope().set_client(None)`.
- **Acceso:** `ssh -i ~/.ssh/muci -o IdentitiesOnly=yes root@muci.org`. El
  `IdentitiesOnly` no es opcional desde esta máquina.
- **El clasificador de permisos corta** `scp`, los heredocs por SSH y las consultas raras a la
  base. Sí pasan: `git archive | ssh`, `tar -c | ssh`, tuberías a `python3 -`, y `python -c`
  inline.
- **Ventana para tocar producción:** evitar 00/06/12/18 UTC (reinicios automáticos del cron) y
  en particular las 00:00 UTC, cuando corre `sync_bims_contacts`.

### Task 1: Backup verificado de las cuatro bases

**Files:**
- Create: `backup-bases.sh`

**Interfaces:**
- Consumes: nada.
- Produces: `/root/bk/db-pre-django52.sql.gz` en el servidor, y un script reutilizable.

**Insumo requerido:** la contraseña de `anthropic_readonly` para MariaDB, exportada como
`MYSQL_PWD` por quien corre el script. No está en el repo y el clasificador bloquea leerla del
`.env` de producción.

- [ ] **Step 1: Verificar que hay espacio en disco antes de escribir 2,5 GB**

```bash
ssh -i ~/.ssh/muci -o IdentitiesOnly=yes root@muci.org 'df -h / | tail -1; free -g | head -2'
```

Esperado: al menos 5 GB libres en `/`. Si hay menos, parar y avisar: un disco lleno en el
servidor de facturación es peor que un Django viejo.

- [ ] **Step 2: Escribir el script**

```bash
cat > backup-bases.sh <<'EOF'
#!/usr/bin/env bash
#
# Dump de las cuatro bases del servidor. Primer backup que van a tener.
#
# POR QUÉ ESTE USUARIO
#   La credencial de root de MariaDB no está a mano: /root/.my.cnf no existe y
#   /etc/mysql/debian.cnf existe pero no se honra. `anthropic_readonly` tiene
#   GRANT SELECT, SHOW DATABASES ON *.*, que alcanza para un dump.
#
# DOS COSAS QUE NO SON OPCIONALES
#   --no-tablespaces: ese usuario no tiene el privilegio PROCESS y sin esto falla.
#   set -o pipefail: con el pipe a gzip, $? refleja el gzip y MIENTE. Ya reportó
#   éxito sobre un gzip vacío de 20 bytes.
#
# USO
#   MYSQL_PWD=<pass> ./backup-bases.sh [etiqueta]
set -euo pipefail
set -o pipefail

ETIQUETA="${1:-$(date -u +%Y%m%dT%H%M%SZ)}"
DESTINO="/root/bk/db-${ETIQUETA}.sql.gz"
BASES="muci muci-integrador krayin moodle"

if [ -z "${MYSQL_PWD:-}" ]; then
    echo "ERROR: exportá MYSQL_PWD con la clave de anthropic_readonly" >&2
    exit 2
fi

mkdir -p /root/bk
echo "==> Volcando: $BASES"
mariadb-dump -u anthropic_readonly -B $BASES \
    --single-transaction --quick --no-tablespaces \
  | gzip > "$DESTINO"

echo "==> Verificando que el dump esté completo"
ULTIMA="$(zcat "$DESTINO" | tail -1)"
if ! echo "$ULTIMA" | grep -q "Dump completed on"; then
    echo "ERROR: el dump NO terminó bien. Última línea: $ULTIMA" >&2
    exit 1
fi

echo "==> OK  $DESTINO  ($(du -h "$DESTINO" | cut -f1))"
echo "    última línea: $ULTIMA"
for b in $BASES; do
    n="$(zcat "$DESTINO" | grep -c "^-- Current Database: \`$b\`" || true)"
    echo "    base '$b' presente en el dump: $n"
done
EOF
chmod +x backup-bases.sh
```

- [ ] **Step 3: Mandar el script y correrlo**

```bash

  'tar -x -C /root && chmod +x /root/backup-bases.sh && MYSQL_PWD="$MYSQL_PWD" /root/backup-bases.sh pre-django52'
```

Nota: `MYSQL_PWD` tiene que estar en el entorno de la sesión SSH. Si no se puede propagar,
correr el script desde el servidor pasando la variable ahí.

Esperado: `==> OK /root/bk/db-pre-django52.sql.gz (~<varios cientos de MB>)`, la última línea
con `Dump completed on`, y **las cuatro bases presentes con `1` cada una**.

- [ ] **Step 4: Confirmar que el archivo es real y no un gzip vacío**

```bash

  'ls -l /root/bk/db-pre-django52.sql.gz; zcat /root/bk/db-pre-django52.sql.gz | wc -l'
```

Esperado: tamaño de cientos de MB (no 20 bytes) y millones de líneas. **Si el tamaño es de

- [ ] **Step 5: Commit**


### Task 3: Un test que cargue el `settings.py` real y corra `check`

**Files:**
- Modify: `core/tests.py`

**Interfaces:**
- Consumes: nada de tareas previas.
- Produces: `SettingsRealTest.test_el_settings_de_produccion_pasa_check`.

**Por qué existe:** hoy no hay **ningún** entorno que corra el settings real sobre Django
moderno. Es el único test que habría atrapado el `ImproperlyConfigured` del driver antes de
reiniciar el servicio. Corre en un subproceso porque el settings hace `dotenv_values(".env")`
en el import y no se puede reconfigurar Django dentro de un test.

- [ ] **Step 1: Escribir el test que falla**

Agregar al final de `core/tests.py`:

```python
class SettingsRealTest(TestCase):
    """
    El `settings.py` de produccion tiene que importar y pasar `check`.

    La suite corre con `test_settings`, que carga 4 apps y esquiva `drf_yasg`,
    `corsheaders` y el admin. Este test cubre el settings real, que es donde
    vive el riesgo de un upgrade de Django: un `ImproperlyConfigured` ahi se
    manifiesta al ARRANCAR el servicio, no al correr los tests.
    """

    def test_el_settings_de_produccion_pasa_check(self):
        import os
        import subprocess
        import sys
        import tempfile
        from pathlib import Path

        raiz = Path(__file__).resolve().parent.parent

        # El settings hace `dotenv_values(".env")` relativo al cwd, asi que se
        # corre en un directorio temporal con un .env sintetico. Nunca se toca el
        # .env real, que ademas no existe en local.
        with tempfile.TemporaryDirectory() as tmp:
            Path(tmp, ".env").write_text(
                "SECRET_KEY=solo-para-el-check\n"
                "DEBUG=False\n"
                "ALLOWED_HOSTS=localhost\n"
                "DB_NAME=no_se_conecta\n"
                "DB_USER=no_se_conecta\n"
                "DB_PASSWORD=no_se_conecta\n"
                "DB_HOST=127.0.0.1\n"
                "DB_PORT=3306\n"
                "WOOCOMMERCE_URL=http://test.local\n"
                "WOOCOMMERCE_KEY=k\n"
                "WOOCOMMERCE_SECRET=s\n"
                "BIMS_URL=http://bims.test.local\n"
                "BIMS_USER=u\n"
                "BIMS_PASSWORD=p\n",
                encoding="utf-8",
            )

            codigo = (
                "import os, django\n"
                "os.environ['DJANGO_SETTINGS_MODULE'] = 'muci-integrador.settings'\n"
                "django.setup()\n"
                # Sin esto el check queda registrado como cliente de produccion en Sentry.
                "import sentry_sdk; sentry_sdk.get_global_scope().set_client(None)\n"
                "from django.core.management import call_command\n"
                "call_command('check')\n"
            )
            entorno = dict(os.environ, PYTHONPATH=str(raiz))
            resultado = subprocess.run(
                [sys.executable, "-c", codigo],
                cwd=tmp,
                env=entorno,
                capture_output=True,
                text=True,
                timeout=120,
            )

        self.assertEqual(
            resultado.returncode,
            0,
            "el settings real no pasa `check`:\n%s\n%s"
            % (resultado.stdout, resultado.stderr),
        )
```

```python
    def test_el_changelist_del_admin_de_ordenes_responde(self):
        """
        `FailedOrderAdmin` gano `bims_sale_id` y `bims_invoice_number` en
        list_display y search_fields el 2026-08-28, sin cobertura. Un nombre de
        campo mal escrito ahi es un error 500 en la pantalla que usa Carlos.

        User.objects.create_superuser("admin-test", "admin@test.local", "clave-de-test")
        self.client.login(username="admin-test", password="clave-de-test")

        FailedOrder.objects.create(
            order_id=202707,
            status=FailedOrder.COMPLETED,
            message="Procesado con éxito.",
            bims_sale_id="31301",
            bims_invoice_number="12000",
        )

        respuesta = self.client.get("/admin/core/failedorder/")
        self.assertEqual(respuesta.status_code, 200, respuesta.content[:400])

        # La busqueda por numero de factura es la razon de ser del campo.
        busqueda = self.client.get("/admin/core/failedorder/?q=12000")
```
